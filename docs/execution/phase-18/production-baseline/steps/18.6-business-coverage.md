# Step 18.6 — Aggregate business and integration coverage

## Outcome

Extend the protected Phase 18 baseline with the remaining evidence categories
already represented by canonical records: lead flow, staff workload, support
pressure and integration health. It remains a read-only, whole-platform
aggregate collector—not a customer analytics feature.

## Inputs, ownership and exclusions

- Source decision: Phase 18 work package 18.1.
- Depends on: steps 18.1 through 18.5 and the existing deployed migrations.
- Owns the Phase 18 baseline workflow and its documentation/evidence only.
- Does not write any application schema, API, event, identity, billing,
  tenancy, infrastructure topology, paid provider or canonical record.

## Frozen data boundary

Schema `1.2` adds only integer counts:

- `business.leads`: daily lead intake, daily confirmed bookings and overdue
  open task count;
- `business.support`: open-ticket and unresponded-SLA-breach count;
- `business.integrations`: daily sync mutation/conflict, pending delivery and
  stale-active-installation count.

The PostgreSQL query uses only explicit `count(*)` scalar subqueries. It never
reads or retains subjects, descriptions, names, contact details, owners,
customer IDs, organization IDs, installation IDs, payloads, event types,
statuses, errors or timestamps from individual records. Earlier record
versions remain valid during the transition.

## Verification, capacity and rollback

1. Validate schema versions `1.0`, `1.1` and `1.2`, including rejection of an
   unexpected field.
2. Run one protected capture and one protected review, retaining only redacted
   run links and aggregate summary in Git.
3. The once-daily scalar query adds no data store, index, service, API or paid
   provider. Incremental recurring cost remains $0.
4. Rollback is removing the `1.2` write path; legacy records and all production
   services remain unaffected.
