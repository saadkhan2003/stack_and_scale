# Step 18.5 — Aggregate operational coverage

## Outcome

Extend the Phase 18 baseline record with existing, aggregate-only request and
outbox health values. The change fills the evidence-plan gap without adding
customer telemetry, a product feature, an external vendor, or a new data store.

## Source decisions and predecessors

- Phase 18 work package 18.1 (evidence and prioritization).
- Predecessors: 18.1 through 18.4.
- Inputs: the current Prometheus metric contract, durable outbox schema, and
  protected baseline workflow.

## Ownership and prohibited writes

- Owns: `.github/workflows/phase18-production-baseline.yml`, this child-plan
  documentation, its verification evidence and the capacity-ledger row.
- Does not write application schemas, API contracts, event semantics, identity,
  billing, tenancy, infrastructure topology, paid-provider configuration or
  customer records.

## Field boundary

The `1.1` record adds only the following numeric fields:

- `traffic.completedRequests24h`, `traffic.serverFailures24h`, and
  `traffic.averageRequestDurationMilliseconds24h` from Prometheus `sum(...)`
  queries;
- `outbox.pending`, `outbox.processing`, `outbox.deadLetter`, and
  `outbox.oldestUndeliveredAgeSeconds` from a fixed aggregate SQL query.

No route, label, request, query string, account, organization, event ID,
payload, error string, credential or individual identifier can enter the
record. Existing `1.0` host/database-only records remain reviewable so a
schema addition does not erase the evidence already collected.

## Actions and verification

1. Add the frozen versioned allowlists to capture and review logic.
2. Obtain only scalar Prometheus API results from the existing internal
   monitoring network and fixed aggregate SQL results from PostgreSQL.
3. Validate finite non-negative values, then retain the same 90-day files.
4. Check formatting and execute a protected capture/review after merge.

## Capacity, cost, privacy and rollback

- The queries read existing 14-day Prometheus data and PostgreSQL aggregates;
  no new service, index, storage, background worker or billable provider is
  introduced. Incremental recurring cost is $0.
- The fixed sums are intentionally low-cardinality and execute once per day.
- Rollback is removal of the added fields/workflow revision; the prior
  host/database evidence remains valid and no production service is changed.
