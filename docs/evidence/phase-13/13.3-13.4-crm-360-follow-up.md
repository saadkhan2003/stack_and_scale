# Phase 13.3/13.4 CRM 360 and Follow-up Evidence

## Delivered

- Extended the protected lead detail response with a chronological, append-oriented `timeline` composed from the lead, activity, note, task, booking and opportunity records already stored in PostgreSQL.
- Kept factual records separate from append-only notes. A synthetic `lead.created` entry anchors the record; subsequent lifecycle changes remain the existing activity audit events.
- Added normalized ISO timestamps and explicit timeline kinds/event types for deterministic rendering and audit review.
- Added task assignment and due-date controls, a completion control, and server-derived task semantics: `open`, `overdue`, or `completed`.
- Defined overdue as an incomplete task whose non-null `due_at` is earlier than the current database time. Completed tasks are never overdue. Overdue tasks receive derived `high` urgency; all other tasks receive derived `normal` urgency.
- Kept email, phone, original enquiry, and consent in a separately labeled, non-editable sensitive-fields section. No sensitive fields are copied into activity metadata by these changes.
- Preserved the existing `crm:read` and `crm:manage` access checks and added the web proxy for the existing completion endpoint.

## Existing-schema limits

The current `platform.lead_tasks` table has no priority, status, or task-comment columns, and this phase does not add a migration. Task status and priority are therefore derived from `completed_at` and `due_at`; narrative comments use the existing auditable lead-notes workflow and remain visibly separate from factual events. Custom task priorities, task-specific comments, and reassignment history require a future schema contract change.

## Sound cues

The existing `minimal` UI SFX pack remains in use. Opening a lead uses `open`; successful saves and task creation use `success`; successful task completion uses `check`; failed operations use `error`. No cue is played for passive timeline rendering or list scrolling.
