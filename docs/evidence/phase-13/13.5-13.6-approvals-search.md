# Phase 13.5/13.6 Evidence

## Scope

Implemented generic tenant-scoped approvals and authorized PostgreSQL
operations search. The migration is additive: existing lead rows remain valid
with a nullable organization field, while new operations search requires an
explicit organization match.

## Authorization evidence

- Approval request/read permissions: `owner`, `admin`, `manager`.
- Approval decision permission: `owner`, `admin`.
- Operations search permission: `owner`, `admin`, `manager`.
- `member` has none of these permissions.
- Approval requester and approver must be different actors.

## Data handling evidence

Search queries scope leads, tasks and operations documents by the server-side
organization ID before returning rows. Results are bounded to 25 and document
excerpts are capped at 160 characters. Search responses do not contain document
bodies, email addresses or message fields.

Approval transitions write `platform.approval_audit_trail` and the existing
`platform.audit_events` stream with correlation ID and non-sensitive metadata.

Approval lifecycle semantics are explicit and policy-bound:

- Requests are limited to governed actions: discounts, proposals, refunds,
  destructive changes, permission changes, API credentials, license overrides,
  invoice write-offs, contract exceptions and provisioning.
- `reminder_at` and `escalation_at` are server-derived from expiry; lifecycle
  processing is idempotent through `reminded_at` and `escalated_at` markers.
- Expired pending requests are persisted as `expired` and receive both the
  approval trail event and the general audit event. Reminder/escalation notices
  use the existing notification service and remain tenant-scoped.
- Approval decisions still require the existing permission and separation of
  duties checks; lifecycle processing cannot approve or reject a request.
- Lifecycle integration coverage verifies approval-trail and general audit
  records for reminder and expiry events.

## Verification record

The focused API and web tests are `apps/api/test/operations.integration.test.ts`,
`apps/api/test/crm.integration.test.ts` and
`apps/web/test/staff-operations-search.test.ts`. They cover policy rejection,
