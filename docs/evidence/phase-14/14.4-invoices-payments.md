# Phase 14.4 Evidence

## Delivered

- Tenant-scoped invoices with draft, approval, issue, due, partial, paid, overdue, void and refunded states.
- Issued financial totals and line items are protected by database immutability triggers.
- Payment attempts are separate from append-only payment events and allocations.
- Explicit methods: `bank_transfer`, `easypaisa`, `jazzcash`, `raast`, and `cash`.
- Attempts start pending; verification requires a different actor from the recorder.
- Proof and reference fields have tenant-scoped duplicate detection at application and database boundaries.
- Partial and multi-invoice allocations are recorded as events; reversal, correction and refund are compensating events.
- Verified attempts can produce one idempotent receipt record.
- Provider callbacks require an adapter, signature verification, provider event idempotency and persisted payload hash.
- Fee, payer, received-time and receiving-account/till fields are retained for reconciliation.

## Configuration Boundary

Tax configuration remains per line item and no tax rate is embedded in the invoice workflow. Provider truth is supplied through `PAYMENT_PROVIDER_CALLBACK_SECRET` and the `PaymentProviderAdapter`; redirects are not accepted as verification.

## Verification Scenarios

Contract tests cover explicit invoice transitions and method validation. API integration coverage should run with PostgreSQL for tenant isolation, approval segregation, duplicate evidence, all five methods, pending-to-verified transitions, allocations, compensating events, receipts and signed duplicate callbacks.
