# Phase 14.5-14.6 Evidence

## Accounting readiness

- The versioned contract is `ACCOUNTING_EXPORT_VERSION = 1` in
  `packages/contracts/src/accounting.ts`.
- Exports normalize timestamps, sort by occurrence, kind, and id, and serialize
  stable payload keys. Import keys are tenant and contract-version scoped:
  `organization:kind:record:v1`. Explicitly linked correction exports may reuse
  a period while an uncorrected period remains unique. The record
  ledger rejects duplicate import keys and is append-only. Corrections retain
  `correctionOf`; no source event is deleted or overwritten.
- `platform.accounting_imports` records adapter/import-batch outcomes and
  prevents replay per tenant, adapter, and import key. `platform.accounting_mappings`
  records source-to-external identifiers without coupling the core model to a
  vendor.
- `AccountingAdapter` is a provider-neutral contract. No paid accounting
  provider is selected or enabled.

## Support operations

- Tickets, comments, pauses, escalations, attachment metadata, and events are
  tenant-scoped in migration `0014_phase_14_5_14_6_accounting_support.sql`.
- Public comments and internal notes use separate visibility values. Public
  comments start the first-response clock; pause intervals are excluded from
  elapsed SLA time and remain auditable.
- Status, ownership, escalation, comment, and SLA changes append support events.
  Blob uploads are intentionally outside this step; attachments have a storage
  metadata hook only.
- API access resolves the existing server-side membership and role matrix before
  any tenant query. Accounting export is owner/admin only; managers can read
  accounting exports and manage support; members can read and cannot mutate.

## Verification notes

Focused contract tests cover deterministic ordering, correction references,
stable import keys, and overlapping pause semantics. Full repository checks are
run as part of the Phase 14 closeout.
