# Phase 15.6 — assurance and controlled rollout

## Release controls implemented

- Every portal area is feature flagged per client organization and defaults to
  disabled in the database migrations.
- Client administrators can only manage members of their own client
  organization. A person must have an existing identity record (created by a
  first sign-in) before an administrator can add them. Add and revoke actions
  are recorded in an append-only portal membership-event table; an
  administrator cannot revoke their own access through this endpoint.
- The browser portal exposes this member-management flow only to a resolved
  `client_admin`. Its Next relay accepts only the exact member list, grant and
  revoke paths; it cannot be used as a general-purpose API proxy.
- Portal responses use client-safe projection tables and bounded query limits.
- Browser mutations are relayed through explicitly allow-listed Next routes;
  arbitrary API paths are not exposed by the browser relay.
- Sensitive browser pages are dynamic and send `no-store` responses through
  their API relays. The portal page is marked `noindex`.
- Project, review, commercial, files, support and activity boundaries are
  independently enforced in the API, rather than relying on a web-page check.

## Production rollout evidence

### 2026-08-31 isolated QA client validation

- A dedicated, non-customer client organization with all applicable portal
  flags enabled was exercised in production through the normal OIDC browser
  flow. The account resolved as an active `client_admin` and the portal rendered
  only that organization's projections.
- A request for an unrelated client-organization identifier returned the
  portal's sign-in/authorization boundary rather than any cross-client data.
- A clearly marked synthetic support request and public replies were submitted
  through the portal. The request persisted after a page reload. A browser-only
  form-reset defect found during the first reply was corrected in `822b023`.
  Production delivery run `33404082300` completed successfully, and the
  post-deploy reply rendered its success message with no console errors.
- The billing-notification preference was disabled, verified after a reload,
  then restored and verified enabled after a second reload. The security
  preference remained mandatory and disabled to editing.
- Browser console capture contained no error-level messages before or after the
  QA mutations. The support-comment form defect above was a visible client
  error, not an API failure, and its fixed production behavior was re-tested.

### 2026-08-31 protected host assurance

- Protected assurance run `33405211972` seeded one isolated review request.
  The client administrator accepted it in the portal, received the success
  message, and the request disappeared after reload.
- Protected assurance run `33424229976` wrote a capacity snapshot on the
  production host. The raw snapshot remains on the protected host because it
  contains operational details; its command completed successfully.
- Protected assurance run `33424274876` disabled only the isolated QA portal
  organization. The client portal immediately returned the authorization
  boundary while the staff workspace remained available. Run `33424319624`
  restored the flag, and the authorized QA portal recovered successfully.

### Controlled assurance mechanism

The protected GitHub Actions workflow
`.github/workflows/phase15-rollout-assurance.yml` performs the remaining
operations without exposing deployment credentials:

1. seed one isolated QA review request, then record its portal decision;
2. capture a host capacity snapshot;
3. disable the isolated QA portal flag, verify access is denied while staff
   operations remain available, then restore the flag and verify recovery.

The operations above completed successfully and are retained as the repeatable
release/rollback mechanism for future portal releases.
