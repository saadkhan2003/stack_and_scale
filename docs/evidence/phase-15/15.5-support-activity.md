# Phase 15.5 — support, activity and notification projections

## Implemented local contract

- Portal members are resolved from an active portal membership before every
  request. The client organization feature flags independently control support,
  activity and notification views.
- Support reads are restricted to the calling client organization's canonical
  customer record. Only public ticket data is returned; internal comments,
  staff owners, escalations, attachments and audit metadata are absent.
- The portal can create a normal-priority support request or append a public
  client comment. It cannot set severity, priority, owner, status or internal
  visibility. These writes reuse the canonical Phase 14 support service.
- The browser portal exposes both request creation and public replies for only
  the caller's customer-scoped ticket list. The private relay permits those
  two exact write routes and no arbitrary support API path.
- Activity is read solely from explicitly client-safe portal projections.
- Notification preferences are stored only for the authenticated user's own
  billing and system categories. Security notifications are displayed as
  immutable and cannot be disabled.

## Verification

- API and web TypeScript checks pass in the local workspace.
- Contract suite: 15 files, 71 tests passing.
- `portal-access.integration.test.ts` covers ticket creation, public comments
  and foreign-ticket denial, but it requires a PostgreSQL-capable runner. The
  current Codex sandbox cannot connect to the configured local PostgreSQL port
  (`EPERM`), so this integration test must be run in CI or on the development
  host before release.

## Rollback

Set the affected client organization's `portal_support_enabled`,
`portal_activity_enabled` or `portal_notifications_enabled` flag to `false`.
This removes portal access without deleting the canonical support or activity
records.
